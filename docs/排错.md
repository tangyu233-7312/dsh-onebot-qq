# 排障（Troubleshooting）

> 先跑两个命令，多数问题能定位：
> ```bash
> node bin/dsh-onebot-qq.mjs doctor          # 环境/配置/端口（✅/⚠️/❌）
> dsh --profile web --dump-config     # 插件行挂上没有
> ```

## 〇、第一步：一键诊断（推荐先做）

控制台 设置 → QQ 控制台 →「运维」→ **🩺 一键诊断 / 导出运维报告**：

- 自动检查：配置校验 / 主人 QQ / DSH agent preset / 原生工具注册 / 协议端连接（OneBot v11） / 人设 /
  数据目录可写 / 生图（可选）/ 链接解析（可选）/ 运行信息（版本、Node、平台、路径）；
  总耗时 ≤6s（连接检查 5s 超时）。
- 生成一份**脱敏 Markdown 报告**：`<dataDir>/reports/diagnose-YYYYMMDD-HHmmss.md`；
  弹窗显示结论摘要（✅/❌/⚠️）、报告保存位置和正文，可「复制报告」「复制给 DSH 的修复提示词」。
- **交给 DSH 本体修复**：把报告路径贴给 DSH，说一句「按这份报告修复 dsh-onebot-qq」即可
  （报告里有分步建议和复检命令）。
- 隐私：token / API Key 原值**不会出现**（只写"已配置/未配置"）、QQ 号/selfId 已打码、
  URL 里的凭据参数替换成 `***`。报告仍含本机路径与内网地址，公开前请自行检查。
- 和 CLI `node bin/dsh-onebot-qq.mjs doctor` 的区别：doctor 是轻量命令行自检（环境/配置/端口/人设，
  不写报告）；控制台诊断额外查 DSH preset、工具注册、目录可写、生图/链接解析，并生成可交给 DSH 的报告。

## 一、日志在哪、怎么看

- DSH 的终端/服务日志里，本插件所有输出都带前缀：`[onebot-qq:kernel]`、`[onebot-qq:onebot]`、
  `[onebot-qq:pacing]`、`[onebot-qq:compat]`、以及各子插件的 `[onebot-qq:<id>]`。
- 正常启动应有：
  ```
  [onebot-qq:kernel] 内核就绪（契约 v1，插件 13/13，工具 10，命令 7）
  [onebot-qq:onebot] OneBot WS 已连接
  ```
- 聊天留档（开 `archive.enabled`）在 `<dataDir>/logs/qq_chat/<kind>_<id>.jsonl`。

## 二、连不上协议端（OneBot v11）

> **先点控制台里的测试按钮**：设置 → QQ 控制台 →「运维」页 → **「测试 OneBot 连接」**（先保存输入框再测），
> 看它返回什么（页面上会直接显示结果；等价于 `kernel.checkOneBot()`）。
> 再点 **「重新连接 OneBot」** 可强制重连一次，不用重启 dsh-web。

| 测试返回 / 现象 | 含义与下一步 |
|---|---|
| `ok: false, error: 'OneBot 未连接'` | 插件还没连上 WS：确认协议端已启动、`onebot.wsUrl` 正确、token 一致 |
| `ok: false` + 超时 / 连接失败 | WS 端口不通：协议端是否监听该端口、是否被防火墙拦、是否容器/WSL 的 `127.0.0.1` 指错 |
| `ok: true` 但发不出消息 | 看 `onebot.httpUrl` / `httpToken`（HTTP API 与 WS 是两套地址） |
| 向导里协议端项一直 ❌ | 保存后是否自动连接成功；必要时点「重新连接 OneBot」或重启 dsh-web |

| 现象 | 检查 |
|---|---|
| 日志反复 `OneBot 连接失败` / `WS 断开` | `onebot.wsUrl` 是否指向协议端的**正向 WS**（不是 HTTP）；`ws://127.0.0.1:3001` 是默认 |
| `401` / `token 不匹配` | 协议端开了鉴权 → 填 `onebot.wsToken` / `onebot.httpToken` |
| WS 连上但发不出消息 | `onebot.httpUrl` 是否指向 **HTTP API**（默认 `http://127.0.0.1:3000`）；通过 `curl` 验证 |
| 一切配置都对但连不上 | 协议端进程与 QQ 登录状态（协议端 WebUI 看 QQ 是否在线；SnowLuma 看 `get_status` 的 `online`/`good`）；端口是否被防火墙/代理拦 |
| 本机没有 QQ | `autoConnect: false` 做静态验证；`npm test` 跑假协议端端到端 |
| 用 `dsh` 的容器/WSL | `127.0.0.1` 在 WSL 里指向 WSL 自己；改用宿主 IP 或 `--network host` |

> 端口探测：`node bin/dsh-onebot-qq.mjs doctor` 会 TCP 探测 WS/HTTP 端口（`--no-net` 跳过）。

## 二·二、接了 SnowLuma 之后

> 先分清两层：**插件 ↔ 协议端**（WS/HTTP 连不连得上）和**协议端 ↔ QQ**（hook 注入没注入、登录没登录）。
> SnowLuma 的 WebUI（默认 `127.0.0.1:5099`）里「概览 / 进程」页能直接看到注入与登录状态，比猜快。

| 现象 | 原因 | 处理 |
|---|---|---|
| WS 连不上 / `401` | SnowLuma 的 3000/3001 **强制带 `accessToken`**（多数实现可以裸跑） | 在 WebUI 的 OneBot 配置或 `config/onebot.json` 里抄两个 token，分别填 `onebot.wsToken` / `onebot.httpToken`；地址不用改 |
| 日志「OneBot WS 已连接」但插件行为怪 | 这句是**连接成功的正常日志**（连 SnowLuma 也是这句）；旧版配置的 `napcat.*` 会被自动兼容 | 正常，不用改；看控制台「测试 OneBot 连接」返回的 selfId 对不对 |
| 注入失败（WebUI 进程里 `injected:false`） | ptrace 权限不足、或 QQ 进程被 Electron 子进程混淆 | 用 root，或给 node 授权 `setcap cap_sys_ptrace=ep "$(readlink -f "$(which node)")"`（换 Node 要重做）；`/proc/sys/kernel/yama/ptrace_scope=3` 会让注入彻底失效；确认注入的是 QQ **主进程**（不是 `--type=zygote/renderer/utility`） |
| 注入了、能发消息但**收不到**（`get_status.good=false`） | hook 卡住：发得出、收不进 | 插件健康检查会显示「接收链路异常」；重启协议端栈（`systemctl restart <你的 snowluma 栈>` / 重跑启动脚本） |
| QQ 自动掉登录 / 提示版本异常 | QQ **静默热更新**把版本换了，hook 与版本错位 | 冻结热更新：`echo "0.0.0.0 qqpatch.gtimg.cn" | sudo tee -a /etc/hosts`；必要时重装匹配的 QQ 版本再重启栈 |
| 扫码页二维码一直不刷新 / 页面打不开 | 二维码**约 2~3 分钟就过期**，纯截图脚本不会自己点「刷新」 | 截图脚本要能识别过期提示（如「当前二维码已过期」）并自动点「刷新」；或直接用 VNC/noVNC 看桌面扫码 |
| 群里 `#sl` 时**框架和机器人各回一句** | SnowLuma 自带 `#sl` 状态指令，`swallow:false` 时还会把该消息继续下发给机器人 | 关掉：`statusCommand.enabled=false`（协议端配置，热生效）；只想挡下发就设 `swallow:true` |
| 群文件/视频看不了、`get_file` 拿不到 | SnowLuma 的 `get_file` **只覆盖图片/语音缓存** | 属于协议端能力差异：入站群文件/视频溯源可能降级，聊天本身不受影响；用 `list_images` 看已落盘的图片 |
| 引用/撤回偶发失效 | SnowLuma 的 `message_id` 是**有符号 int32，负值合法** | 用消息事件里的真实 `message_id` 原样传，别自己加减；插件已支持负值（2026-10-27 起） |

## 二·补、两种"升级/重装后"的坑

| 症状 | 原因 | 处理 |
|---|---|---|
| QQ 线又能调用 `ops_bash` / `spawn_teammate` 等本机工具 | **opsgate 的 bundle 顺序被打回**：`dsh plugin add` 会把新装的 bundle `push` 到 `dsh.profile.bundles` 末尾，于是 opsgate 排在 `dsh-onebot-qq` **之前**，它的 preset 补丁 `patch: entry "preset-qq-chat" not found` 被静默丢弃 | `dsh --profile web --dump-config 2>&1 \| head -1` 不能出现 `patch: entry` 报错；`… \| sed -n '/^- id: preset-qq-chat/,/^- id:/p' \| grep -c dsh-onebot-qq-opsgate` 必须 = 1。不对就手改 profile `package.json` 的 bundles 顺序（先备份），再重启 |
| 重装插件后，之前的修复"消失"了 | 插件目录是真实目录，`dsh plugin remove/add` 整个换掉 → **本地热修全丢** | 按 `docs/` 之外的维护记录 `patches/` 逐个重打（从旧到新），再重启验收 |

## 三、模型工具不出现 / 不调用

1. **工具是否注册**：日志「工具 10」；控制台「状态」页也有工具列表。
2. **插件是否挂载**：`dsh --profile web --dump-config` 里应有 `dsh-onebot-qq` 行；没有就是没装/没选 bundle。
3. **preset 是否裁掉了工具**：QQ 线用的 agent preset 若禁用了 `tool-*` 相关行，模型就看不到工具；
   用 `dsh.agentPreset` 指到你的 QQ 聊天 preset（示例见 `examples/presets/qq-chat.patch.yml`）。
4. **模型没调工具**：把「必须调 `mcp__qq__send_message`」写进 QQ 线的 `AGENTS.md`
   （安装模板已包含；如果你改没了，模型可能只在正文里回话 → QQ 端收不到）。
5. **工具名对不上**：改了 `toolPrefix` 后，人设/指令里的旧工具名就失效了；一般不要改。

## 四、图片发不出

| 现象 | 常见原因 | 处理 |
|---|---|---|
| 工具返回「不在白名单」 | 图片不在 `file-transfer.imageWhitelist` 目录内 | 把图放进白名单目录（默认数据目录与系统临时目录）；白名单是 realpath 判定，软链目标也要在范围内 |
| 工具返回成功但 QQ 没图 | 协议端读不到本地文件（不在同一台机器/权限不足/路径形式不对） | 先确认协议端和 DSH 在同一台机器；再试 `DSH_QQ_MEDIA_REF=fileUri` 重启，详见下文 |
| Windows 上图发不出 | 路径含中文/空格/逗号；各实现对 `file=` 形式接受度不同 | 见 [Windows 安装](Windows安装.md) 的 CQ 文件引用真机验证清单 |
| 生图失败 | 未配置 `credentials.gptImage` / 环境变量；中转站不可达；冷却中 | 看 `[onebot-qq:imagegen]` 日志；冷却返回 `{blocked:true}` 属正常，等冷却结束 |

**CQ 文件引用模式**（唯一开关：环境变量 `DSH_QQ_MEDIA_REF`）：

- 默认 `fwd`：绝对路径、Windows 反斜杠转正斜杠（`C:/data/qq/a.png`）。
- `fileUri`：`file:///C:/data/qq/a.png`（需要时切换）。
- 两种都要在真机上实测一次（不同协议端实现/版本行为不同），选定后写进部署环境变量。

## 五、Windows 权限与 symlink

- 普通用户默认**不能创建文件软链**：人设投递自动降级为**复制模式**（功能正常；切人设时复制文件）。
  想用软链：Windows 设置 → 开发者选项 → 打开「开发者模式」，或用管理员账号。
- `chmod 600` 在 Windows 基本无效：用 `icacls` 收紧配置权限（见 [安装与卸载 §九](安装与卸载.md#九权限与凭据)）。
- 长路径（>260 字符）可能报 `ENAMETOOLONG`：把数据目录放到短路径（如 `C:\dsh-data\qq-bot`）。
- 杀毒/索引器可能占用文件导致 rename 失败：内核原子写自带重试（3 次退避）；仍失败时看日志里的 `EPERM/EBUSY`。

## 六、端口占用

| 端口 | 用途 | 冲突处理 |
|---|---|---|
| 3001 / 3000 | 协议端 WS / HTTP | 改协议端配置与 `onebot.*Url` 保持一致（换协议端不用改地址，只改 token） |
| 3971 | 可选 compat 网关 | `EADDRINUSE` 时检查旧桥/旧脚本；不用就 `compatServer: false` |
| DSH web 端口 | DSH 自己的 `--port` | 与本插件无关 |

compat 网关端口被占只会记日志、不影响内核；确认不需要旧脚本就关掉它。

## 七、配置相关

| 现象 | 原因 / 处理 |
|---|---|
| 日志「实例配置未完成（缺 adminQq）…控制台可继续配置」 | 这是**待配置模式**（正常）：打开 设置 → QQ 控制台 →「新手向导」填主人 QQ / 协议端地址并保存，就绪后自动连接 |
| 启动报「QQ 机器人配置未就绪：onebot.wsUrl 未配置…」 | 除 adminQq 外的必填项错误仍会报错：填 WS/HTTP 地址后重启 |
| 改了 `config.json` 不生效 | 手改需要重启 dsh-web；控制台热改立即生效 |
| 配置文件不存在就被创建了 | 这是刻意的：会写一份默认配置并进入待配置模式（控制台新手向导填写即可） |
| JSON 解析错误 | 检查逗号/引号；Windows 记事本可能有 BOM（内核会剥 BOM，但请确认 JSON 合法） |
| 旧配置读进来不对 | 用 `node bin/dsh-onebot-qq.mjs import-legacy <旧配置>` 落盘迁移并检查报告 |

## 八、消息收不到 / 回了但没人看到

- **只有正文没有工具调用**：QQ 线必须调 `mcp__qq__send_message`（正文只出现在 GUI）。这是最常见原因。
- **被门禁拦了**：`ignoreGroups` / `groupUserBlocklist` / 白名单；看内核日志的 wake/gate 行。
- **群聊没 @**：默认群里要 @/引用/唤醒词才回（`gate-wake.groupAtRequired`）。
- **主动接话没开**：`pacing.reply.enabled=true` 且群号在 `pacing.reply.groups`。
- **重复回复**：检查是否新旧两个消费者同时连同一个协议端（旧 standalone / 另一个 profile）。

## 九、会话不连续 / 报 not-found

- 会话映射在 `<dataDir>/state/sessions.json`；删掉 DSH 会话后映射会变 stale，下一条消息会自动建新会话。
- 想强制重开某条线：`/reset`（当前线）或 `/resetall confirm`（全部）；或停 DSH 后删 `sessions.json` 里的对应项。

## 十、要反馈问题

请附上：

1. `node bin/dsh-onebot-qq.mjs doctor` 的完整输出（**先自己打码 QQ 号/群号/token**）；
2. DSH 日志里 `[onebot-qq:*]` 的 ERROR/WARN 片段；
3. 系统与版本：`node --version`、`dsh --version`、OS、协议端与版本（实现名与版本 + QQ 版本）；
4. 复现步骤（私聊/群聊、是否 @、消息内容类型）。

**不要**贴 `config.json` 原文（含 token）或完整日志路径里的用户名。
